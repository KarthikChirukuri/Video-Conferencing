WebRTC

-> One of most common use of UDP is of WebRTC. which is used for video communication
-> WebRTC - web real time communication 
-> These are mainly built on UDP. These WebRTC works on bidirectional 
-> Here without WebRTC we send videos like from A to server and from server to B and vice versa. But using WebRTC it will establish an bidirectional connection between A and B. We use server based communication when reliability required. 

How does it work?
As said above to establish connection between the two machines like A and B in the above we will use four steps
Signalling, Connecting, Securing and Communicating 

1) Signalling - here we have one signalling server inside which have SDP. Here initially we send request to this signalling server. and this establish the connection between the machines. here for connecting between the two machines it uses IP addresses.
2) Connecting - Here we use ICE (Internet connectivity Establishment) protocol. This protocol takes the IP address and help in establishment of connection 
3) Securing - Here we use two protocols DLTS and SRTP. First here we secure the connection before sending data. Here we use the concept of encryption.
4) Communicating  - Here at last now we start communication. Here we uses protocols like RTP and SCTP. 
-> WebRTC as a technology not needed to be implemented from scratch it is already implemented. we can use it using the API's. 

MediaStream - Which is an API used to collect video and audio from our device. 
RTCPeerConnection and RTCDataChannel - using these we establish data communication between the client.

-> As discussed above we use navigate.mediaDevices to get connect with the media devices here we use the function mainly getUserMedia()
-> This function returns a promise to resolve media stream matching devices. 
-> This function mainly uses the object MediaStreamConstraints object that specifies the requirements that we have.

	const constraints = {
		'video' : true,
		'audio' : true
	};

	navigator.mediaDevices.getUserMedia(constraints)
		.then(stream => {
			console.log('Got MediaStream:', stream);
		})
		.catch(error => {
			console.error('Error accessing media devices.', error);
		})

-> The call to getUserMedia() will trigger a permissions request. If the user accepts the permission, the promise is resolved with a MediaStream containing one video and one audio track. If the permission is denied, a PermissionDeniedError is thrown. 
-> In case there are no matching devices connected, a NotFoundError will be thrown.

	function updateCameraList(cameras){

		if(!listElement) return;
		listElement.innerHTML = '';
		
		cameras.map(camera=>{
			const cameraOption = document.createElement("option");
			cameraOption.label = camera.label;
			cameraOption.value = camera.deviceid;
			return cameraOption;
		})
		.forEach(cameraOption => listElement.add(cameraOption));
	}

Getting started with peer connections

-> Peer connections is the part of the WebRTC specifications that deals with connecting two applications on different computers to communicate using a peer-to-peer protocol.
-> The communication between peers can be video, audio or arbitrary binary data (for clients supporting the RTCDataChannel API).
-> In order to discover how two peers can connect, both clients need to provide an ICE Server configuration
-> This is either a STUN or a TURN-server, and their role is to provide ICE candidates to each client which is then transferred to the remote peer.
-> This transferring of ICE candidates is commonly called signaling

ICE (Interactive Connectivity Establishment)
-> ICE helps two peers discover how to connect over a network.
-> Each peer must be provided with an ICE server configuration.
-> ICE servers generate connection information called ICE Candidates.
-> ICE Candidates represent possible network paths that can be used to establish a connection.

STUN Server
-> A STUN server helps a device discover its public IP address and network information.
-> It is used when a direct peer-to-peer connection is possible.
-> The information obtained from the STUN server is used to generate ICE candidates.
TURN Server
-> A TURN server relays data between peers when a direct connection cannot be established.
-> It is used in cases such as strict NATs, firewalls, or network restrictions.
-> Audio, video, and data pass through the TURN server.

ICE Candidates
-> ICE Candidates are possible connection paths generated using STUN or TURN servers.
Each peer collects its ICE candidates.
-> These candidates must be shared with the remote peer before a connection can be established.

signalling
-> Signaling is the process of exchanging connection information between peers before the actual WebRTC connection is established.
	Step 1: Exchange connection details
	Step 2: Establish WebRTC connection
	Step 3: Start video/audio communication
-> WebRTC provides api for Capturing camera and microphone, Creating peer connections, ICE candidate generation, Audio/video streaming
How signalling is done? Most applications use a server.
Examples: REST API, WebSocket Server, RPC Service
In our project: React Frontend + Spring Boot WebSocket Server

WebRTC Connection Flow
	-> Create a peer connection.
	-> Configure STUN/TURN servers.
	-> Gather ICE candidates.
	-> Create and send an SDP Offer.
	-> Receive and process an SDP Answer.
	-> Exchange ICE candidates through the signaling server.
	-> Establish the peer-to-peer connection.
	-> Start audio, video, or data communication.

Peer A
   ↓
Gather ICE Candidates (STUN/TURN)
   ↓
Create Offer
   ↓
Send via Signaling Server
   ↓
Peer B
   ↓
Create Answer
   ↓
Send via Signaling Server
   ↓
Exchange ICE Candidates
   ↓
Peer Connection Established
   ↓
Audio / Video / Data Communication

Initiating peer connection

-> Each peer connection is handled by RTCPeerConnection object. 
-> the constructor of this class takes a single RTCConfiguration object as parameter. 
-> This Object defines how the peer connection is set up  and should contain information about the ICE servers to use
-> once this is created we will create an sdp offer or answer depending on if we are calling peer or receiving peer
-> once this offer or answer is created then it will be sent to remote peer through diff channels. passing this is called signalling
-> to initiate this peer connection setup from calling side we create RTCPeerConnection and then we call createOffer() to create RTCSessionDescriptionObject
-> this description is set using setLocalDescription() and then over our signalling channel to the receiving side. 
-> We also set up a listener to our signaling channel for when an answer to our offered session description is received from the receiving side.

async function makeCall() {
    const configuration = {'iceServers': [{'urls': 'stun:stun.l.google.com:19302'}]}
    const peerConnection = new RTCPeerConnection(configuration);
    signalingChannel.addEventListener('message', async message => {
        if (message.answer) {
            const remoteDesc = new RTCSessionDescription(message.answer);
            await peerConnection.setRemoteDescription(remoteDesc);
        }
    });
    const offer = await peerConnection.createOffer();
    await peerConnection.setLocalDescription(offer);
    signalingChannel.send({'offer': offer});
}


-> On the receiving side we wait for an incoming offer before we create our RTCPeerConnection instance. 
Once we received we set the received offer as setRemoteDescription()
-> next we call createAnswer() to create an answer to received offer
-> then again we set the answer as local description and sent to the calling side over signalling server
